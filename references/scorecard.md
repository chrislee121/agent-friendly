# 评分卡与等级

## 1. 九个维度

每个维度打 0～4 分，每个分数都要附证据。没有证据按 0 分算。

### D1 可发现

| 分 | 标准 |
|---|---|
| 0 | 没有任何机器可读入口 |
| 1 | 有 robots.txt、sitemap |
| 2 | 至少一种机器可读能力入口：API 文档、OpenAPI、llms.txt、已注册的系统意图 |
| 3 | 发布了标准发现文件（api-catalog、MCP Server Card、Agent Card、App Intents / AppFunctions / 鸿蒙意图已注册），且内容与实际一致 |
| 4 | 多种入口内容一致；已登记到生态目录（MCP Registry、平台连接器目录）；有版本和变更通知 |

### D2 可理解

| 分 | 标准 |
|---|---|
| 0 | 关键内容只在图片、Canvas 或纯客户端渲染里 |
| 1 | HTML 能读，但语义差：无标签、div 当按钮 |
| 2 | 语义 HTML 和无障碍基本合格；有结构化数据 |
| 3 | 提供 Markdown 协商或 llms.txt；实体有稳定 ID；有术语表和面向 agent 的说明 |
| 4 | 内容理解经过评测验证（agent 对关键问题的回答正确率有数据） |

### D3 可操作

| 分 | 标准 |
|---|---|
| 0 | 只能通过界面操作 |
| 1 | 有 API，但没有面向 agent 设计：缺文档或 schema |
| 2 | 关键只读任务有结构化工具，契约检查无 error |
| 3 | 主要任务的读写都覆盖；以任务为单位切分；有输出 schema 和分页 |
| 4 | 多步流程有工作流或组合工具；支持长任务；各接入面行为一致；工具定义有版本治理 |

### D4 身份与授权

| 分 | 标准 |
|---|---|
| 0 | 共享账号密码，或让 agent 模拟登录 |
| 1 | 静态 API Key |
| 2 | OAuth，但授权范围很粗 |
| 3 | OAuth 2.1 + PKCE；细粒度授权范围；令牌绑定受众、短期有效、可撤销；用户能看到已授权的 agent |
| 4 | agent 身份可验证（签名、Web Bot Auth、签名 Agent Card）；委托链可追溯（令牌交换）；资源级授权；增量授权 |

### D5 人的控制

| 分 | 标准 |
|---|---|
| 0 | agent 可以直接执行不可逆动作 |
| 1 | 有确认，但模型可以绕过 |
| 2 | 写操作都有确认 |
| 3 | 按风险分级确认；R3 走系统 UI 或带外渠道且绑定参数；可撤销；有限额 |
| 4 | 带范围和有效期的预授权；三级关停；确认打扰率有数据且受控 |

### D6 可靠性

| 分 | 标准 |
|---|---|
| 0 | 没有错误规范；重试会重复执行 |
| 1 | 有基本的 HTTP 错误码 |
| 2 | 错误信息可行动；限流返回 429 和 Retry-After |
| 3 | 幂等键；乐观并发；长任务异步；结果顺序确定；有超时 |
| 4 | 有 SLO；有版本与弃用策略；契约测试进 CI；做过故障注入 |

### D7 安全

| 分 | 标准 |
|---|---|
| 0 | 没有威胁模型 |
| 1 | 有基础认证 |
| 2 | 输入校验；不可信内容标注来源；令牌不透传；校验 Origin |
| 3 | 致命三角已断开；工具定义有哈希；对抗用例通过；最小权限 |
| 4 | 持续红队；异常检测；供应链审查；外部安全审计 |

### D8 可追溯与合规

| 分 | 标准 |
|---|---|
| 0 | 没有日志 |
| 1 | 有服务端日志，但不含 agent 身份 |
| 2 | 审计日志含 agent、委托人、工具、参数摘要、结果；数据最小化 |
| 3 | 用户能查看 agent 访问记录；agent 表明 AI 身份；隐私政策和内容偏好已更新；有留存策略 |
| 4 | 日志防篡改；完成上线地区的合规评估；定期复审 |

### D9 评测与运营

| 分 | 标准 |
|---|---|
| 0 | 没测过 |
| 1 | 手工试过几次 |
| 2 | 有任务集和终态校验 |
| 3 | 多模型多次运行，pass^k 达到门槛；回归评测进 CI |
| 4 | 线上监控成功率、不安全动作、确认率；失败样本回流任务集；按版本对比 |

## 2. 等级

等级按门槛逐级判定，平均分高不能抵消短板。

| 等级 | 名称 | 门槛 | 含义 |
|---|---|---|---|
| L0 | 不可用 | 未达 L1 | agent 只能靠截图乱点，或被拦在门外 |
| L1 | 可读 | D1 ≥ 2，D2 ≥ 2 | 公开内容能被稳定读懂 |
| L2 | 可查询 | L1 + D3 ≥ 2，D6 ≥ 2，D7 ≥ 2，D9 ≥ 1 | 能通过结构化接口查询 |
| L3 | 可代办 | L2 + D4 ≥ 3，D5 ≥ 3，D8 ≥ 2，D9 ≥ 2，红线全过 | 能代用户做可逆的事 |
| L4 | 可托付 | L3 + 所有维度 ≥ 3，且 D5、D7、D9 = 4 | 能托付高风险的事 |
| L5 | 原生 | 所有维度 = 4 | agent 是一等用户 |

**红线**（见 security.md 第 1 节）：只要有一条不通过，等级最多 L2，验收不通过。系统没有写操作时，与写操作相关的红线可以填 `na`，但要说明原因。

## 3. 加权分

加权分只用来横向比较和跟踪进度，不决定等级。行业剖面会调整权重，见 industries.md。

加权分 = Σ(维度分 × 权重) / Σ(4 × 权重) × 100

## 4. 输入文件格式

```json
{
  "system": "某某系统",
  "profile": "commerce",
  "target_level": "L3",
  "dimensions": {
    "D1": {"score": 3, "evidence": "https://example.com/.well-known/api-catalog"},
    "D2": {"score": 2, "evidence": "Lighthouse 无障碍 92"}
  },
  "redlines": {
    "H1": {"status": "pass", "evidence": "越权测试报告 #12"},
    "H3": {"status": "fail", "evidence": "付款工具未接确认服务"}
  }
}
```

缺失的维度按 0 分计；缺失的红线按未验证计（视同不通过）。
