# 测试与评测

## 1. 六层测试

| 层 | 测什么 | 方法 | 工具 |
|---|---|---|---|
| L1 契约 | schema 合法、注解如实、错误格式统一、命名规范 | 静态检查 + schema 校验 | `scripts/lint_tools.py`；JSON Schema 校验器 |
| L2 业务 | 按模型风格的输入能否正确处理 | 单元与集成测试 | 项目自身测试框架 |
| L3 协议一致性 | 各接入面是否符合平台规范 | 官方检查工具 | MCP Inspector；AppIntentsTesting；`adb shell cmd app_function`；Chrome WebMCP 测试开关；Lighthouse；isitagentready.com |
| L4 Agent 端到端 | 真实模型能否办成 P2 的任务 | 任务集 × 多模型 × 多次运行，校验终态 | `scripts/passk.py` 汇总 |
| L5 对抗 | 注入、越权、重放、绕过限额 | 红队用例 | security.md 第 9 节 |
| L6 灰度 | 真实流量下的表现 | 小比例上线 + 监控 | 审计日志、指标看板 |

### L2 必测的输入

- 空字符串、全空格、超长字符串
- 同义词和别称：「人民币 / 元 / CNY」「明天 / 下周一」
- 越界值：负数、0、超过上限
- 缺少可选参数时（Android AppFunctions 下可选参数会以 null / 0 / false 传入）
- 类型接近但不对：数字写成字符串、日期格式不同
- 不存在的 ID、已删除的 ID、别人的 ID

## 2. 构建评测任务集

- 来源：P2 任务清单、客服工单、站内搜索词、真实 agent 日志
- 每个任务：初始状态、用户原话（≥3 种说法）、金标准终态、风险等级、允许的工具、禁止的动作
- 两类评测分开维护：
  - **能力评测**：初始通过率偏低，用来找短板、指导改进
  - **回归评测**：应接近 100% 通过，用来防止改坏，进 CI
- 规模：先 20～50 个任务，覆盖每个风险等级；每个 R3 任务至少配 1 个对抗变体

### 校验方式（按可靠性从高到低）

1. **终态比对**：直接查数据库或调只读接口，断言状态。首选
2. **规则校验**：调用了哪些工具、参数是否满足约束、是否调用了禁止的工具
3. **模型评判**：只用于无法程序化校验的输出（例如总结质量），要有评分细则，并抽样人工复核

不要因为格式、标点、等价写法不同就判失败。

## 3. 运行

- 至少 2 个不同厂商的模型，覆盖目标用户实际会用的助手
- 每个任务每个模型至少跑 4 次；R3 任务至少 8 次
- 每次从干净的初始状态开始；记录完整轨迹（工具调用、参数、返回）
- 模拟用户：多轮任务用另一个模型扮演用户，按脚本补充信息

## 4. 指标

| 指标 | 定义 | 用途 |
|---|---|---|
| pass^1 | 所有运行的平均成功率 | 能力 |
| **pass^k** | 同一任务 k 次运行**全部**成功的概率，按任务平均。无偏估计：C(c,k) / C(n,k) | **稳定性，验收主指标** |
| pass@k | k 次里至少一次成功的概率 | 只说明「有可能做到」，不能用于验收 |
| 不安全动作率 | 出现禁止动作、越权、未确认执行 R3 的运行占比 | 安全，必须为 0 |
| 稳定解决 / 时好时坏 / 从未解决 | 按任务分类计数 | 找出不稳定的任务优先改 |
| 平均工具调用数 | 每次运行调用工具的次数 | 过高说明工具切分或描述有问题 |
| token 与时延 | 每次运行的总量 | 成本 |
| 澄清率 | agent 向用户追问的比例 | 过高说明参数设计或描述不清 |
| 确认打扰率 | 每个任务触发的人工确认次数 | 过高会让用户习惯性点同意 |

单次成功率 90% 的 agent，连续 8 次都成功的概率只有约 43%。持续运行的系统要看 pass^k。

## 5. 默认验收门槛

项目可以调整，调整要写明理由。

| 风险等级 | 门槛 |
|---|---|
| R0 | pass^4 ≥ 0.90 |
| R1 | pass^4 ≥ 0.85，越权访问 0 次 |
| R2 | pass^4 ≥ 0.80，重复执行 0 次，不安全动作 0 次 |
| R3 | pass^8 ≥ 0.90，未经确认执行 0 次，不安全动作 0 次，对抗用例全部拦截 |

## 6. 结果文件格式

`scripts/passk.py` 读取 JSONL，每行一次运行：

```json
{"task_id": "book_table_basic", "risk": "R2", "model": "model-a", "success": true, "unsafe": false, "tool_calls": 3, "tokens": 4200, "latency_ms": 5100, "confirmations": 1}
```

必填 `task_id`、`success`；`risk` 缺省按 R0 计。

## 7. 改进循环

1. 看「时好时坏」的任务轨迹，找出是选错工具、参数错还是理解错
2. 优先改描述和参数设计，其次合并或拆分工具，最后才改模型侧提示词
3. 改完先跑回归评测，再跑能力评测
4. 让模型在评测里顺带反馈工具哪里难用（Anthropic 的评测做法），作为线索而不是结论

## 8. 上线后监控

- 按周看：任务成功率、不安全动作、确认打扰率、撤销率、错误码分布、agent 来源分布
- 线上失败样本脱敏后补进任务集
- 模型或平台更新、协议升级时，重跑全部回归评测
